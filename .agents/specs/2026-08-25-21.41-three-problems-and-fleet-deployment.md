# Three problems, a checker fleet, and an admin panel

- Builds on `2026-08-25-18.33-online-judge.md`; where the two disagree, this file wins.
- Three problems ship in the repository, seeded into the database: `minimizing-coins`, `rl-nearest-pairs` and `combo`.
- The existing `cf-4-A` Watermelon stays exactly as it is, so the list holds four problems and nothing already submitted is lost.
- Every statement is rewritten to read the same way: a short description, then input, output, constraints and a worked example, with maths through KaTeX.
- Statements are written as Markdown and the problem page renders that Markdown together with the maths, so headings, code blocks, lists and emphasis look the way they were written instead of showing their own punctuation.
- Watermelon's statement is rendered the same way, so all four problems look alike.
- A statement that mentions a function signature shows it as code, which is what makes an interactive problem readable at all.
- `minimizing-coins` is an ordinary problem: one input, one correct answer, compared ignoring whitespace.
- Its package carries eighteen tests and no example, so the example written in its statement becomes the public one and all eighteen supplied tests stay hidden.
- `rl-nearest-pairs` accepts any answer that is optimal, judged by the checker script that ships with it. Twenty tests, the worked example public.
- `combo` is interactive: the person writes a function the grader calls, and answers by calling `press`. Its sixty-nine tests are the official example, kept public, and sixty-eight hidden ones.
- Every hidden test is worth one point in all three problems, so a score reads as tests passed out of tests hidden.
- Where a package states limits, difficulty, rating or tags, those are used. Where it does not, these are: minimizing-coins easy, rating 1000, one second, 256 MB; combo hard, rating 2200, two seconds, 256 MB.
- `combo` is passed or failed, never partly: it is accepted only when the grader reports acceptance on every test. The number of button presses the grader counted is shown next to each test, because that is what the original competition rewarded.
- A `combo` submission that runs past its time limit is a time limit; one that stops without the grader reporting anything is a runtime error; one whose grader prints something we do not recognise is an internal error.
- For an interactive problem the submission is built together with the problem's grader into one program, the test is fed to it, and the verdict is whatever the grader itself reports - nothing is compared against an expected file.
- A public test of an interactive problem shows the test itself and what the grader answered, in place of the expected and actual output that an ordinary problem shows.
- `combo` accepts C++ only, because its grader exists only in C++, Java and Pascal. Its language picker offers nothing else.
- The other two accept Python and C++.
- C++ is now compiled and run by our own checkers, in the same sandbox as Python. The external OIOIOI service and the C++ adapter that called it are removed from the project.
- A submission in a language a problem does not accept is refused when it is sent, with a message naming what that problem does accept.
- Each checker machine runs a small web service on itself; the app asks it to judge and asks it for the answer. Checkers no longer fetch work by themselves.
- That service answers three things: whether it is healthy and how busy it is, a request to judge one submission, and the result of a submission it was given.
- Every call to a checker carries the shared key. A call without it is refused.
- The app reaches each checker through a permanent SSH tunnel opened from the application machine, so the checker's service listens only on its own loopback and is invisible from the internet.
- No firewall rule is added on any machine; the SSH port that already exists is the only way in.
- The queue stays in Postgres. A dispatcher inside the app hands waiting submissions to machines that are online, enabled and not full, and writes back what they answer.
- When no machine can take work, the submission waits in the queue and the page says checking is temporarily unavailable. It is never failed for that reason.
- A machine that stops answering has its unfinished submission returned to the queue, and another machine picks it up. Three such losses in a row mark that submission as an internal error.
- Redis is removed: the app dispatches directly, so there is nothing left to wake up.
- A submission that was being judged when the system is upgraded goes back to the queue and is judged again by a machine speaking the new way. Nothing already finished is touched.
- `/admin` lists every machine: its name, its address, whether it is reachable, whether it is enabled, how many submissions it is judging right now, when it last answered, and how many it has judged in total.
- A machine can be disabled and enabled from that list. A disabled machine is given no new work; whatever it is already judging is allowed to finish.
- The panel sends a batch of submissions on request: pick a problem and how many, and it sends a mixture of correct and deliberately wrong solutions.
- Those solutions ship with the repository, one correct and one wrong per problem, so a batch needs no file from the person running it.
- Roughly seven in ten are correct and the rest wrong, so a run shows several verdicts rather than one.
- A batch submission is an ordinary submission by a built-in account named `benchmark`. It appears on the homepage, in the ranking and in solve counts exactly like anyone else's.
- A batch is at most five hundred submissions, only one batch runs at a time, and it can be stopped while it is running.
- Each problem's batch uses a language it accepts: Python where allowed, C++ for `combo`.
- While a batch runs the panel shows how many submissions per minute are being finished, against how many machines are working, and the verdicts as they land.
- The panel is reachable by anyone who knows the address. This is a deliberate choice for this deployment and is written down as such.
- One command sets up the whole system from a fresh checkout: the application machine and every checker machine.
- Machines are listed in one inventory file. Adding or removing a checker is one line there and the same command again.
- The application machine ends up running Postgres, the app, and a proxy that obtains a certificate for the configured domain by itself, so the site answers over HTTPS.
- Until a domain is configured the site answers over plain HTTP on the machine's address, and adding the domain later is a config change and the same command again.
- Every checker machine ends up with the checker service, the three problems' test data on its own disk, and the sandbox tools the judge needs.
- Problem data reaches the machines during setup. No contest data is baked into any image.
- Running the command a second time changes only what differs, and does not disturb submissions being judged.
- Secrets - the shared key, the database password, the certificate contact - come from a file that stays out of the repository.
- The deployment is run against the thirteen checker machines and the one application machine listed by the user.
