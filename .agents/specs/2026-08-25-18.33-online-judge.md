# Online Judge

- Architecture, deployables and porting sources are locked by `2026-08-25-18.14-merge-best-of-ai-prompt.md`; this file locks the product decisions on top of it.
- The `note` module, its table, seed, integration test and homepage components are deleted once the problem list replaces them.
- Interface copy is English throughout. Problem statements render in whatever language they were imported in.
- Dark and light themes with a header toggle; the chosen theme applies before first paint, so the page never flashes the wrong one.
- `/` is the problem list plus a recent-activity panel of the newest submissions from everyone.
- The problem list offers search by code or title, filters by difficulty, tag and kind, sort by code, title, difficulty, rating, kind or solve count, page size 25/50/100, and previous/next paging.
- Filtering, sorting, counting and paging happen in Postgres, not in the browser.
- Search matches parts of a problem's code or title and ignores capitals. The list starts sorted by code, ascending.
- A problem is addressed by its slug, so its page lives at `/problems/cf-4-A`.
- The problem page puts the statement on the left and the submit panel on the right, stacking to one column on narrow screens.
- Statements render as plain text with `$…$` and `$$…$$` maths through KaTeX. No Markdown parsing.
- The problem page shows time limit, memory limit, I/O mode, test count, solve count, tags, difficulty, and every public sample with its input and output.
- The editor is Monaco, matching the site theme, with the language picker offering Python and C++ only.
- Source can also be dropped onto the editor or picked as a file, up to 2 MB, replacing the editor content.
- A dropped or picked file whose extension names one of the allowed languages switches the picker to it.
- Logging in takes only a username of letters, digits, `_`, `-` or `.`, at most 64 characters. No password. An unknown name is created on first login.
- The signed-in name is kept in a cookie set by the server; a submission is always attributed to that cookie's user and never to a user id sent by the browser.
- Typing a name someone already uses signs you in as that person. Names are deliberately unprotected, so anyone knowing a name can read that person's solutions.
- Signing out is an action in the header. Left alone, the login lasts thirty days.
- Anyone may browse problems, submissions and rankings without logging in.
- An anonymous visitor sees the editor but a disabled submit button telling them to log in.
- Submitting anything other than Python or C++ is refused at submit time with a validation message and never queued.
- Submitting saves the solution and answers success even when the wake-up channel is down; a sweeper picks such a submission up and it is still judged.
- The submission page refreshes itself every second while the solution is queued or running, and stops the moment the result is final.
- Sample test results show input, expected output, actual output and any message.
- Hidden test results show only the test number, pass/fail verdict, time and memory. Their input, expected output and actual output are never returned by any endpoint.
- All tests are run even after one fails, so the per-test list is always complete.
- When tests fail in different ways, the submission carries the verdict of the first failing test.
- A solution is accepted only when every test passes.
- The score is the points of the passed hidden tests; the maximum is the points of all hidden tests. Samples are worth nothing. The submission page shows it as earned out of total.
- A solution that fails to compile shows the compiler message and no test rows.
- A submission's own page - source, per-test rows, compiler message and score - opens only for its author. Everyone else sees its row in a list and nothing beyond it.
- "My submissions" lists the signed-in user's own submissions; an anonymous visitor asking for it is sent to the login page.
- Submission statuses are queued, running, accepted, wrong answer, time limit, memory limit, runtime error, compilation error and internal error, each with its own colour; queued and running pulse.
- The global ranking orders users by how many distinct problems they have an accepted solution for, and settles equal counts by who reached that count first.
- Only people with at least one accepted solution appear in the global ranking.
- A problem's solve count is how many distinct people have an accepted solution for it.
- Each problem page carries its own ranking: everyone with an accepted solution, earliest accepted first.
- Rankings are visible without logging in.
- Backend modules `account`, `task`, `submission` and `ranking` replace `note`, each a vertical slice under `src/backend/modules/`.
- Postgres stores users, problems, per-test metadata (number, visibility, points), submissions and per-test results. Hidden test data is never stored there.
- Sample input and expected output are stored in Postgres. Hidden test files exist only on the checkers' filesystem.
- Judging a submission is claimed with a time-limited lease carrying a fencing id, at most three attempts, heartbeats while it runs.
- A sweeper re-queues submissions whose lease expired, and marks a submission internal error once its attempts are exhausted.
- A checker that has just judged a problem keeps taking that same problem's waiting submissions before listening for new work again.
- Python is judged by the sandboxed checker under `checkers/bwrap/`; C++ is handed to `checkers/cpp/`, which submits it to OIOIOI.
- When OIOIOI is unreachable, the C++ submission stays queued and its page says C++ checking is temporarily unavailable; it is judged once the service returns.
- Being unable to reach OIOIOI does not use up one of a submission's three attempts, so an outage never turns it into an error - it waits as long as the outage lasts.
- Both checkers report progress and results to one internal endpoint on the app, authorised by a shared key header rather than a cookie.
- A submission that already has a final result ignores any later report about it.
- The sandboxed checker compiles once per submission, then runs each test with a hard kill at twice the time limit, measuring CPU time and peak memory.
- A run is judged over memory first, then time, then a non-zero exit, and only then compared for correctness.
- Output comparison ignores differences in whitespace; a problem may instead name a checker script that scores between 0 and 1, where only a full score passes.
- A problem's difficulty, rating, tags, kind, limits, points and test count all come from its package, never from a value typed into code.
- One problem ships in the repository: Codeforces 4A "Watermelon", allowing Python and C++, easy, rating 800, one second, 64 MB, with one sample and its hidden tests.
- Problem test files live in a repository folder mounted into every checker container, identical on every replica and never baked into an image.
- Seeding is idempotent: it inserts nothing when the problem is already there.
- The app, Postgres 17, Redis and both checkers all start locally from Docker Compose, and checkers can be scaled to several replicas.
- Every setting comes from environment variables. No host name, port, key or path is written into source. `.env.example` documents each one.
- The app answers `GET /api/health` and `GET /api/ready`; every service declares a healthcheck and a stable container name.
- OIOIOI is a separate optional service documented as a third runtime dependency and never part of the app image.
- There are no screens for creating or editing problems; problems arrive only by seeding.
- There are no passwords, roles or permissions beyond the username cookie.
