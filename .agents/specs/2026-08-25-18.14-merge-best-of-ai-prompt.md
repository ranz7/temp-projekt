## Product shape

Browser talks only to the Next.js app. The app owns Postgres and Redis. Submitting a solution inserts a `queued` row and wakes workers (`XADD` or equivalent). Workers are a **separate deployable**, horizontally scaled, **stateless**: job payload + package fetch + write result, then forget. Redis is a wake-up. The submission row is the source of truth. If Redis is down, submit still succeeds (201-equivalent) and a sweeper re-queues.

**Language routing**

- `cpp` / `c++` → C++ worker (OIOIOI adapter from scalable-backend).
- Every other supported language → bwrap/cgroup worker from `judge/` (Python and C++-via-bwrap may exist in that code; do not use bwrap for product C++ if OIOIOI is the chosen C++ path).
- Unknown language → CE / validation error at submit time, never a silent drop.

## Two deployables, one git repo

```
src/                 Next.js UI + tRPC API + Drizzle (one process, one VM later)
deploy/web/          Dockerfile, compose, env example for the app (+ local Postgres/Redis)
checkers/            separate Python (or mixed) project: workers only
  bwrap/             judge from ksi-internships (non-C++)
  cpp/               OIOIOI adapter from scalable-backend
deploy/checker/      Dockerfile(s) for workers, compose for local scale-out
```

Frontend and backend are **one Next.js project** on **one machine**. Checkers are **another project** in this repo, run on **many machines**, ideally with no local disk state beyond a scratch workdir that is deleted after each job. Problem tests and hidden packs come from object storage or an HTTP URL on each job. Do not bake contest data into the worker image.

OIOIOI for C++ is an external service the C++ worker calls. Document it as a third runtime dependency (like Postgres), not as part of the Next.js image. Keep it out of the web container.

## Architecture locks (this repo, not FastAPI)

Reimplement the KSI Postgres **domain** as tRPC modules under `src/backend/modules/`, Kraken rules: `router.ts`, `schema.ts`, `endpoints/{queries,mutations}/<verb-noun>/{index.ts,input.dto.ts,output.dto.ts}`, named exports, `type` not `interface`, uuid v7 from Postgres, every `db.update`/`db.delete` has `.where()`. Public HTTP for the browser is tRPC. Do **not** keep a FastAPI process as the app API.

Modules at minimum: `account` (minimal login as in KSI Vite: username, no password theatre unless the source already has a real scheme), `task` (problems), `submission`, `ranking`. Drop `note` once the homepage is the problem list.

Port the KSI Mongo **frontend** into `src/app/`: problem list, problem detail + editor, submissions list/detail, theme. Add ranking and auth screens from the Vite SPA. User-facing copy can stay Polish where those UIs are Polish. Code, commits, comments: English.

Workers speak a versioned JSON contract (steal scalable-backend `CONTRACT.md`): enqueue job, fetch package, POST result with a shared `SERVICE_KEY`. Idempotent: a terminal `done`/`failed` ignores duplicates. The Next app exposes an internal results endpoint (header key), not a cookie.

## Docker from scratch (this pass)

Everything a VM will run later must already run in Docker locally.

- `deploy/web/Dockerfile`: multi-stage bun install + `next build`, non-root, `output: 'standalone'` if that matches Next 16, `GET /api/ready` and `GET /api/health`.
- Local `docker compose` for web + Postgres 17 + Redis. App config **only** from environment (`DATABASE_URL`, `REDIS_URL`, `SERVICE_KEY`, public app URL, checker wake settings). No IPs or hostnames in source.
- Checker images: bwrap worker needs privileged or the documented cgroup/bwrap capabilities; C++ worker is a thin HTTP client to `OIOIOI_URL`. Both: health endpoint, graceful shutdown, scratch volume, `--scale` locally.
- Pin image tags. `.env.example` documents every variable. Secrets never in git.

**Prepared for Ansible, no Ansible yet.** Do not add `infra/**/ansible`. Shape the repo so a later pass can copy algoacademy.pl: Ansible renders `*.compose.yml.j2` + `*.env.j2`, `docker compose up -d`, waits on container health. That means: one compose file per service, env-file driven, named healthchecks, stable container names, no `network_mode: host` unless unavoidable, no bind-mount of the git tree in the production-shaped compose (copy/build image instead). Local override compose for bind-mounts is fine and must stay separate.
